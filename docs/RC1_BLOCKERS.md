# RC1 Blockers

This file is the git-tracked RC1 board for MPRD. It separates:

- gates that are now automated and expected to stay green, from
- gaps that still block an honest "release candidate 1" claim.

Do not treat "CI green" as equivalent to "RC1 ready". RC1 requires both.

## Automated Gates

These are currently expected to pass through tracked workflows or release-gate runs on tracked branches:

- `cargo fmt --check`
- `RISC0_SKIP_BUILD=1 cargo clippy --workspace --all-targets -- -D warnings`
- `RISC0_SKIP_BUILD=1 cargo test --workspace --all-targets`
- `cargo audit` / `cargo audit --no-fetch` in the dedicated Cargo Audit workflow
- tracked fuzz smoke campaign in `.github/workflows/fuzz-smoke.yml`
- tracked network replay receipt comparison in `.github/workflows/network-replay.yml`
- tracked policy-menu Tau receipt comparison in `.github/workflows/policy-menu-tau-equivalence.yml`

These gates are necessary, but not sufficient, for RC1.

## Remaining RC1 Blockers

- Runtime refinement still stops short of one top-level concrete execution theorem.

  - Narrowed further: the tracked Lean bundle now also includes a concrete composition theorem linking the stronger attestation-hash signed-registry serve path to the shipped `idempotent_file` sink, so the strongest shipped local-effect lane now requires both the richer serve attestation-hash facts and the concrete durable local-file barrier facts when both models describe the same successful execution.
  - Narrowed further: the tracked Lean bundle now also includes a concrete composition theorem linking the stronger attestation-hash signed-registry serve path to the shipped `idempotent_http` sink, so the strongest shipped remote-effect lane now requires both the richer serve attestation-hash facts and the concrete pending/committed HTTP barrier facts when both models describe the same successful execution.
  - Narrowed further: the tracked Lean bundle now also includes top-level refinement theorems linking the richer attestation-hash-plus-ready-packet signed-registry serve model directly to both shipped sink lanes, so the strongest local and remote effect paths now each carry both the richer serve facts plus an abstract `MPRD_ExecutionBoundary` witness through the exact signed-registry packet lane, together with the concrete sink barrier facts, instead of hanging off the older attestation-hash serve model alone.

  - Narrowed further: the tracked Lean bundle now also includes a grouped signed-registry execution-artifact compiler/refinement bridge proving that once the shipped grouped execution artifact exists and its grouped `ExecutionReadyPacketV1` admissions hold, there is one canonical exact signed-registry packet for the next proof step, so this lane no longer has to reconstruct the exact packet by hand from separate grouped runtime artifacts before refining into the abstract execution boundary.

  - Remaining gap: the top-level signed-registry serve refinement theorem no longer needs an explicit witness parameter, the shipped runtime now materializes concrete binding/packet/refinement artifacts for both the grouped ready-packet model and the richer attestation-hash serve model, and the exact-packet lane now has one grouped execution-artifact compiler, but the remaining semantic gap is still exact discharge of each abstract binding/executor field from shipped runtime objects and hashes by one fully concrete proof chain.

Both fail closed if registry attestation metadata drifts or the governance gate input disagrees with the state-prepared rails.

  - Narrowed further: the shipped production `mprd serve` path now also uses the real registry-bound verifier derived from the signed checkpoint, instead of a stub local verifier, before it reaches the concrete ready bridge and side-effect boundary.
  - Narrowed further: proofs now carry a deterministic `execution_authorization_hash_v1` over the attested policy/state/governance packet, and the concrete registry/governance bridge re-derives and checks that hash fail-closed before rebuilding the live ready bundle.
  - Narrowed further: the concrete ready-bridge constructor now also refuses to attach signed-registry bridge facts unless the live ready bundle already carries an admitted execution-authorization witness, and unless the proof still carries matching `execution_authorization_hash_v1` metadata at bridge time.
  - Narrowed further: `AttestationReadyBundle` now carries the exact constructor-gated execution-authorization attestation packet, so proof stamping no longer re-derives the attested policy/state/governance packet from loose `token + state + optional governance` fields at each attestor boundary.

  - Narrowed further: the concrete ready-bridge constructor now also re-hashes that preserved registry tuple against the admitted policy hash fail-closed before attaching it, so the live bridge packet rejects tuple drift instead of trusting adjacent metadata plus a loose digest.
  - Narrowed further: the live `ExecutionRegistryBridgeWitnessV1` now projects through one shared core helper into a grouped bridge attestation packet language, and the tracked Lean bundle includes a local bridge-projection packet proving that this execute-path projection is extensionally equal to the old loose registry tuple plus optional checkpoint language.
  - Narrowed further: the tracked Lean bundle now also has a signed-registry bridge-witness packet proving that reachable executed states on this path require registry-authorization hash binding and preservation of the concrete bridge witness into the rebuilt ready bundle.
  - Narrowed further: the tracked Lean bundle now has a lightweight signed-registry bridge packet proving that reachable executed states on this path require registry resolution, exact checkpoint binding, execution-authorization binding, governance alignment, and ready-bundle rebuild.
  - Narrowed further: the tracked Lean bundle now also has a joined signed-registry execution-boundary packet proving that reachable executed states on this path require those bridge facts plus the concrete execution guards (verified, allowed, replay, binding, executor).
  - Narrowed further: the shipped concrete HTTP/webhook/file executors now emit the admitted governance fields explicitly on the `execute_ready(...)` path, so real side-effect payloads and audit trails no longer have to recover governance context only from the generic proof-metadata map.

### Tier 0: Distributed / Network Resilience

- Network chaos is not yet release-complete.
  - Narrowed: the tracked replay-model series now has a consolidated RC1 receipt at `docs/receipts/rc1_network_replay_20260328.json`, so the remaining gap is no longer "network safety evidence is scattered".
  - Missing: replayable chaos campaigns for stale checkpoints, checkpoint withholding, quorum degradation, Tau/API outages, and related partition schedules.
- Global at-most-once execution across crash and partition scenarios is not yet a shipped end-to-end theorem.
  - Narrowed: the tracked replay-model series now includes a crash-ordering effect-finalization packet, so the safety story no longer stops at replay ownership or visibility alone. The model shows that if a durable effect-commit barrier survives crash and retry, late nonce finalization can still complete without a second external effect emission.
  - Narrowed further: the shipped HTTP, webhook, and audit executor surfaces now all emit the same deterministic `execution_idempotency_key_v1` derived from the policy/state/action/nonce tuple, so downstream services no longer have to reconstruct that tuple ad hoc to enforce retry idempotence.
  - Narrowed further: trustless/private production `mprd serve` now rejects the plain append-only `file` executor and requires the per-nonce `idempotent_file` sink for file-based side effects, so the shipped production file path no longer advertises a local side-effect mode that cannot act as a retry barrier.
  - Narrowed further: the tracked replay-model series now also includes `idempotent_file_effect_barrier`, a concrete adapter-facing local-file safety packet showing that the shipped per-nonce file sink acts as both the side effect and the durable barrier, so later writers short-circuit idempotently instead of emitting a second local effect.
  - Narrowed further: the tracked Lean bundle now also includes a top-level `idempotent_file` production packet proving that successful local execution on the shipped signed-registry serve path requires the serve-boundary facts, explicit `idempotent_file` selection, configured audit-file binding, and the durable local file barrier before success.
  - Narrowed further: trustless/private production `mprd serve` now also rejects plain `http` and requires `execution.executor_type = "idempotent_http"` plus a local effect journal. The shipped remote-effect path now writes a fail-closed pending or committed barrier keyed by `execution_idempotency_key_v1`, blocks automatic replay while a pending barrier exists, and only short-circuits retries after a committed marker is durable.
  - Narrowed further: the tracked replay-model series now also includes `idempotent_http_effect_barrier`, a concrete adapter-facing safety packet showing that the shipped pending/committed HTTP barrier blocks duplicate remote effect emission on retry while pending is unresolved and only allows idempotent short-circuiting after commit.
  - Narrowed further: trustless/private production `mprd serve` now refuses startup if the configured `idempotent_http` journal already contains unresolved `.pending.json` barriers, and both `serve status` and `mprd doctor` surface those pending barriers explicitly instead of reporting only the journal root path.
  - Narrowed further: the shipped operator API now exposes a deterministic `/api/effect-barriers/pending` inventory for unresolved `idempotent_http` barriers, and `/api/alerts` promotes those barriers into the existing incident stream instead of leaving them visible only through status polling.
  - Narrowed further: the protected operator API now also supports explicit dry-run and live manual resolution of a validated pending HTTP barrier by `(policy_hash, idempotency_key_v1)`, either clearing it or promoting it to committed without relying on ad hoc filesystem edits.
  - Narrowed further: the shipped operator API now also exposes a deterministic `/api/effect-barriers/committed` inventory with the same filename/payload drift checks as the pending surface, and committed markers now carry explicit `automatic` versus `manual_promote` provenance so operators can distinguish normal success from manual recovery instead of treating committed files as opaque markers.
  - Narrowed further: the shipped status and doctor surfaces now summarize committed HTTP barriers by `automatic`, `manual_promote`, and legacy-without-provenance buckets, and `mprd doctor` warns if manual-promote barriers are present even when no pending barrier remains.
  - Narrowed further: the tracked replay-model series now also includes `idempotent_http_startup_pending_barrier`, a concrete deployment-facing packet showing that a restarted server stays blocked on unresolved pending HTTP barriers until they are explicitly cleared or promoted to committed.
  - Current state: this still needs tighter runtime and deployment closure before it becomes a shipped end-to-end theorem.

### Tier 1: Operational / Policy Admission

- Owner namespace, node assignment, activation epoch, and certification-tier admission are not first-class yet.
  - Current state: authority is cryptographic and fail-closed, but not yet modeled as "which namespace this node should obey".
- Source mapping still is not universal across every runtime surface, but the shipped registry-bound production proving and verifying helpers, plus the direct registry-bound policy-authorization provider and verifier, now enforce it by default.
  - Narrowed further: the shipped trustless/private `mprd serve` startup path now instantiates that same registry-bound production attestor/verifier pair and fails fast on missing required policy-source mapping, so this is no longer only a per-request runtime guarantee.
  - Current scope: the shipped production `mprd serve` path is still MPB-specific; it now selects the first authorized MPB policy explicitly and fails fast at startup if the configured registry bundle has no authorized `mpb-v1` policy.
  - Remaining gap: non-registry-bound or explicitly relaxed surfaces can still opt out, so RC1 claims must stay scoped to the production registry-bound path.

## Release Rule

MPRD should not be described as "RC1" until:

1. all automated gates above are green on the candidate branch, and
2. every Tier 0 blocker above is either closed or explicitly downgraded out of the RC1 claim.
